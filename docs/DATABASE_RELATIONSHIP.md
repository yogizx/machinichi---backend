# Machinichi — Database Relationships
Generated by Claude · Phase 0 deliverable · Reflects the schema as it exists today (MongoDB/Mongoose)

## 1. Entity relationship overview

```
User (1) ──────────────< Address (many)
User (1) ──────────────< RefreshToken (many)
User (1) ──────────────< LoginAudit (many)
User (1) ────────────── Cart (1, sparse-unique on userId)
User (1) ────────────── Wishlist (1, unique on userId)
User (1) ────────────── SavedForLater (1, unique on userId)
User (1) ──────────────< Order (many)
User (1) ──────────────< Review (many)
User (1) ──────────────< Payment (many)
User (1) ──────────────< ReturnRequest (many)

Category (1) ──────────< Category (many, self-ref via parentCategory)
Category (1) ──────────< Product (many)

Product (1) ──────────< InventoryLog (many)
Product (1) ──────────< Review (many)
Product (1) ──── embedded ─── Product.variants[] (not a separate collection)

Cart (1) ──── embedded ─── Cart.items[] (each references Product)
Wishlist (1) ──── embedded ─── Wishlist.products[] (each references Product)
SavedForLater (1) ──── embedded ─── SavedForLater.items[] (each references Product)

Order (1) ──── embedded ─── Order.items[] (each references Product, denormalized snapshot)
Order (1) ──────────────< Payment (in practice 1, schema allows many)
Order (1) ──────────────< ReturnRequest (many)
Order (1) ──────────────< Review (many, via optional orderId)
Order (1) ────────────── Coupon (many-to-one via couponId)

Coupon (1) ──────────────< Order (many, usage tracking)
Coupon: applicableCategories[] → Category, applicableProducts[] → Product

ReturnRequest (1) ──── embedded ─── ReturnRequest.items[] (each references Product)
```

**Note on normalization:** `Order.items`, `Cart.items`, `Wishlist.products` intentionally denormalize product name/image/price at the time of the action (standard e-commerce practice — an order must show what the customer actually paid, even if the product is later edited or deleted). This is correct design, not a duplication bug.

## 2. Collections and their key relationships

| Collection | Primary relationships | Notes |
|---|---|---|
| `User` | 1—many: Address, Order, Review, Payment, RefreshToken, LoginAudit; 1—1: Cart, Wishlist, SavedForLater | `role` field drives RBAC: `customer` / `admin` / `super_admin` |
| `Category` | self-referencing (`parentCategory`) for subcategories; 1—many → `Product` | |
| `Product` | many—1 → `Category`; 1—many → `InventoryLog`, `Review`; embeds `variants[]` | Single source of truth for both inventory and listing data — see audit doc section 2 |
| `InventoryLog` | many—1 → `Product`, `User` (performedBy) | Append-only audit trail, one row per stock mutation |
| `Cart` | many—1 → `User` (or anonymous via `sessionId`); embeds `items[]` referencing `Product` | TTL index (`expiresAt`) auto-expires abandoned guest carts |
| `Wishlist` | 1—1 → `User`; embeds `products[]` referencing `Product` | |
| `SavedForLater` | 1—1 → `User`; embeds `items[]` referencing `Product` | |
| `Coupon` | many—many → `Category`, `Product` (applicability filters); many—1 ← `Order` (usage) | |
| `Order` | many—1 → `User`; embeds `items[]` (denormalized `Product` snapshot); many—1 → `Coupon` | Has two status-like fields today (`status`, `orderStatus`) — flagged in audit as needing consolidation |
| `Payment` | many—1 → `Order`, `User` | One row per Razorpay order attempt; supports refund tracking |
| `Review` | many—1 → `Product`, `User`; optional many—1 → `Order` | Gated to delivered/returned orders at creation time (logic present, reliability flagged in audit) |
| `ReturnRequest` | many—1 → `Order`, `User`; embeds `items[]` referencing `Product` | Has its own status + timeline, separate from `Order.orderStatus` |
| `Address` | many—1 → `User` | |
| `RefreshToken` / `LoginAudit` | many—1 → `User` | Auth/session security records |

## 3. Product lifecycle (Inventory → Listing → Published → Purchased)

```
┌──────────────┐
│ Admin creates │  POST /admin/products
│ product       │  publishStatus = 'unlisted', isVisible = false, status = 'Draft'
└──────┬────────┘  → InventoryLog entry: type='admin_adjustment', reference='initial_stock'
       │
       ▼
┌──────────────────┐
│ Inventory-only    │  GET/PATCH /admin/inventory, /admin/products/:id/inventory
│ stock management  │  Adjusts quantity/warehouseStock/reorder levels.
│ (Step 2)          │  Never touches publishStatus or isVisible.
└──────┬─────────────┘  → Every change logged to InventoryLog
       │
       ▼
┌──────────────────────┐
│ Admin opens Product   │  Product Listing screen (admin/pages/ProductListing.jsx)
│ Listing form (Step 3) │  Fills marketplace fields: description, images, SEO, variants,
│                       │  badges, marketplace links. Can "Save Draft" (stays unlisted)
└──────┬─────────────────┘  or "Publish to Store".
       │
       ▼ (Publish)
┌──────────────────────┐
│ REQUIRED_TO_LIST gate  │  Server validates: ≥1 image, sellingPrice > 0, category set,
│ (Step 5)               │  description present. Rejects publish if any missing.
└──────┬─────────────────┘
       │ pass
       ▼
┌──────────────────────┐
│ publishStatus =        │  Product now visible on storefront via
│ 'published'             │  GET /products (public controller filters
│ isVisible = true        │  publishStatus: 'published' unconditionally)
└──────┬─────────────────┘
       │
       ▼
┌──────────────────────┐
│ Customer adds to cart  │  checkStock() → reserveStock()
│                        │  quantity -= n, reservedQuantity += n
└──────┬─────────────────┘  → InventoryLog: type='reservation'
       │
       ▼
┌──────────────────────┐
│ Customer checks out    │  ⚠️ Currently broken/unsafe — see ENTERPRISE_AUDIT.md §1.1-1.4.
│ and pays               │  Intended flow after Phase 1 fix:
│                        │  Order created from Cart → Razorpay payment →
│                        │  on payment.captured: deductStock() (reservedQuantity -= n,
│                        │  totalSales += n) → InventoryLog: type='sale'
└──────┬─────────────────┘
       │
       ▼
┌──────────────────────┐
│ Order fulfilment       │  Intended (post Phase 1/5) one-way status flow:
│                        │  Pending → Packed → Shipped → In Transit →
│                        │  Out for Delivery → Delivered
│                        │  (Cancelled only reachable before Packed;
│                        │   restores stock via releaseStock — not yet implemented)
└──────┬─────────────────┘
       │ status = Delivered
       ▼
┌──────────────────────┐
│ Customer can review    │  createReview() checks Order exists with
│ the product             │  status delivered/returned for this user+product
└────────────────────────┘  → Review.isApproved = false until admin approves
                              → approved reviews feed Product.averageRating (via
                                aggregation in getProductReviews; Product.averageRating
                                itself is not yet auto-recalculated on approval —
                                verify/implement in Phase 5)
```

## 4. Cart → Checkout → Payment → Order data flow (as designed; current bugs noted inline)

```
Cart.items[]                    (source of truth for what the customer intends to buy)
   │
   │  checkout.controller.getCheckoutSummary()
   │  → recomputes subtotal/tax/shipping from live Cart + Product data (not stale cart prices)
   ▼
Checkout summary (ephemeral, not persisted)
   │
   │  checkout.controller.placeOrder()   ⚠️ currently throws — missing orderTotal field
   │  Should: validate stock, create Order (snapshot of Cart.items), clear Cart
   ▼
Order (status: Pending, paymentStatus: Pending)
   │
   │  payment.controller.createPaymentOrder()  → Razorpay order created, Payment doc created (status: created)
   ▼
Razorpay Checkout UI (client-side)
   │
   │  payment.controller.verifyPayment()
   │  → verifies HMAC signature against Razorpay order+payment ID
   ▼
   ├─ valid   → Payment.status = captured, Order.paymentStatus = paid, Order.status = confirmed
   │              ⚠️ should also trigger deductStock() here (not currently wired this way)
   │
   └─ invalid → Payment.status = failed, Order.paymentStatus = failed
                  ⚠️ should also trigger releaseStock() here (currently missing — audit §1.3)

Razorpay Webhook (server-to-server, authoritative even if client never calls verifyPayment)
   │
   │  payment.controller.handleWebhook()
   ▼
   ├─ payment.captured → Payment updated with method/bank/wallet detail
   │                       ⚠️ does not currently update Order or trigger stock logic — should mirror verifyPayment's success path
   ├─ payment.failed   → Payment.status = failed
   │                       ⚠️ does not release stock — audit §1.3
   └─ refund.created   → Payment.status = refunded
                           ⚠️ does not restore stock or update Order.paymentStatus — verify in Phase 5
```

## 5. Recommended schema changes (deferred to relevant implementation phase, not done in Phase 0)

1. **Collapse `Order.status` and `Order.orderStatus` into one field** with a single enum matching the required one-way workflow (Phase 1).
2. **New `SearchHistory` collection** for recent/popular search tracking (Phase 3) — doesn't exist today.
3. **`Order.orderTotal` vs `Order.totalAmount`** — pick one, deprecate the other, migrate any existing documents (Phase 1).
4. Consider a **`Notification`-triggered reconciliation job** that periodically cross-checks `Product.reservedQuantity` against the sum of active `Cart.items` referencing it, to catch any drift from the race condition described in audit §1.4 until the atomic-update fix is deployed everywhere.
