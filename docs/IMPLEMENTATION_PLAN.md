## Phase 1 — Fix the order/payment/inventory pipeline (blocks everything else)
**Why first:** Findings 1.1–1.4 in the audit mean the core purchase flow is either broken or unsafe today. Every later phase (cart drawer, reviews, tracking, invoices) assumes orders and stock are trustworthy. Building UI on top of a broken order pipeline means rebuilding that UI later.

**Scope:**
1. Consolidate to a single order-creation path (`checkout.controller.placeOrder`), sourced from `Cart`, never from client-submitted item data.
2. Fix the `orderTotal` missing-field bug and the `shippingAddress` field-name mismatch.
3. Delete `order.controller.createOrder` and the order-creation logic in `payment.controller.createDirectPaymentOrder`; payment flow calls the single fixed path.
4. Move stock deduction to happen only on `payment.captured` (webhook or verified `verifyPayment`), not at order creation. Add `releaseStock` calls on payment failure and on `cancelOrder`.
5. Convert `inventory.service.ts` read-then-write operations to atomic `findOneAndUpdate` with a quantity guard, to close the race condition.
6. Collapse the dual `status`/`orderStatus` fields into one enum matching your required stage names, with server-enforced forward-only transitions.

**Depends on:** Nothing (this is the foundation).
**Estimated impact:** High — touches the money path, needs careful manual testing (place a real test order end-to-end, including a deliberately-failed payment, before moving on).
**Rollback:** Git branch per phase; if a fix regresses, revert the branch. Since this consolidates 3 paths into 1, keep the old code commented/archived in a `legacy/` note in the PR description (not in production code) for one release cycle in case something depended on the dead paths unexpectedly.

## Phase 2 — Remove mock storefront data, connect to real backend
**Why now:** Independent of Phase 1's backend fixes — this is pure frontend rewiring to endpoints that already work correctly (`GET /products`, `GET /products/:slug`, `GET /products/featured`, `GET /products/:id/related`). Low risk, high visible impact, and you specifically asked for this to be the first coding task.

**Scope:**
1. Delete `src/data/products.js`.
2. `Home.jsx` "Trending Collections" → `GET /api/products/featured`.
3. `Product.jsx` → real API only; proper skeleton/empty/error states; **no fallback to fake data under any circumstance**.
4. `ProductDetails.jsx` → fetch real product by slug, real reviews from `Review` model, real related products from `getRelatedProducts`.

**Depends on:** Nothing functionally, but do it after Phase 1 so that "Add to Cart" on real products leads to a working checkout, not the broken one.
**Estimated impact:** Medium — visible to every customer immediately, low technical risk since the fetch code already exists and just needs its fallback removed.
**Rollback:** Straightforward — these are self-contained file rewrites; revert the 4 files if an issue appears.

## Phase 5 — Checkout, order lifecycle, inventory sync, invoices, reviews
**Scope:**
1. Full checkout page per your spec (shipping/billing address, delivery method, promo code, gift note, order summary).
2. Admin order status workflow matching the fixed one-way `orderStatus` enum from Phase 1 (`AdminOrders.jsx` — audit this file in detail at the start of this phase).
3. Dynamic invoice + shipping label generation once status reaches `Packed` (net-new — no generation logic currently exists).
4. Order tracking timeline on the customer side, reading the same `orderStatus`/`statusHistory` fields the admin writes.
5. Review gating to delivered orders only (re-verify 3.3 from the audit once Phase 1's status fix lands).
**Depends on:** Phase 1 (status model), Phase 4 (cart/checkout UI groundwork).
**Estimated impact:** High — this is the largest phase; recommend splitting into 5a (checkout UI), 5b (admin order workflow + invoice/label), 5c (tracking + reviews) as separate PRs even though they're grouped here.
**Rollback:** Each sub-phase (5a/5b/5c) should be its own branch/PR for independent rollback.
